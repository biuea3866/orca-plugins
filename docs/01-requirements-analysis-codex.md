# Orca 플러그인 “Local Self Review” 요구사항 분석

> 작성: Codex (codex-cli 0.154.0, `codex exec`, 2026-10-08). 입력 브리프: Orca 1.4.222 plugin API v0 제약 조사 결과 + 사용자 원문 요구사항. 구현 결정은 [02-design.md](./02-design.md) 참조.

본 문서는 제공된 Orca 1.4.222·plugin API v0 조사 결과를 플랫폼 사실로 사용함. 아래 성능 수치·저장 정책·기능 우선순위는 제품 설계 제안값이며, 플랫폼이 보장하는 값과 구분 필요.

## 1. 요구사항 해석

### 1.1 원문별 구체화

| 원문 | 구체 기능 해석 | 권고 |
|---|---|---|
| Git PR 생성 전 사람 셀프 리뷰 | 로컬 브랜치·작업 디렉터리 변경을 diff로 확인하고, 수정 지시를 코멘트로 기록하는 리뷰 세션 | GitHub PR 생성 없이 시작 가능한 독립 세션 |
| GitHub Pull Request와 동일한 기능 | 파일별 diff, old/new 라인, 멀티라인 코멘트, 스레드, 해결 상태, 변경 요약 | 전체 GitHub 제품 복제가 아닌 아래 포함 범위로 한정 |
| 드래그로 멀티라인 지정·코멘트 작성 | 같은 파일·같은 diff side의 연속 라인 선택 및 스레드 생성 | 마우스 드래그와 키보드 범위 선택 모두 지원 |
| 셀프 리뷰 완료 버튼으로 Claude 또는 Codex 수정 | 저장된 미해결 코멘트를 수정 지시로 변환하고 선택한 에이전트 실행 | 버튼 명칭은 “리뷰 완료 및 AI 수정”; 실행 후 재검토 필수 |
| GitHub에 어떤 기록도 남지 않음 | 리뷰 세션·코멘트·AI 결과를 로컬에 저장하며 GitHub 리소스 변경 금지 | GitHub 댓글·리뷰·PR·브랜치·커밋 업로드 모두 금지 |
| 전체 프로젝트 draft/open PR 목록·상세 | Orca에 등록된 저장소별 GitHub open PR 조회 및 draft 구분 | 읽기 전용 GitHub 조회를 별도 기능으로 제공 |

### 1.2 GitHub PR 기능의 포함·제외

| 기능 | 포함 여부 | 로컬 셀프 리뷰에서의 동작 |
|---|---|---|
| 변경 파일 목록·추가/삭제 통계 | 포함, P0 | 세션의 로컬 diff 기준 |
| 파일별 unified diff·old/new 라인 번호 | 포함, P0 | 고정된 리뷰 스냅샷 기준 |
| split diff | 포함, P1 | 화면 폭에 따른 선택 |
| 단일·멀티라인 코멘트 | 포함, P0 | 로컬 스레드 저장 |
| 코멘트 수정·삭제·스레드 해결 | 포함, P0 | GitHub 전송 없음 |
| 파일별 “확인 완료” 표시 | 포함, P1 | 스냅샷 변경 시 해당 파일 표시 초기화 |
| 전체 리뷰 메모 | 포함, P1 | 특정 라인 없는 세션 메모 |
| 변경 후 코멘트 위치 추적 | 포함, P0 | 일치 확인 실패 시 outdated 표시 |
| PR 제목·작성자·브랜치·상태 조회 | 포함, P0 | 기존 GitHub PR의 읽기 전용 상세 |
| 기존 PR 댓글·리뷰·체크 조회 | 포함, P1 | 원격 데이터 조회 전용, 로컬 코멘트와 구분 |
| GitHub PR 생성·수정 | 제외 | PR 생성 전 로컬 리뷰라는 목적 밖 |
| GitHub 댓글·리뷰 제출 | 제외 | 원격 기록 금지와 충돌 |
| Approve·Request changes | 제외 | GitHub 승인 상태 변경 금지 |
| Merge·Close·Reopen·Ready for review | 제외 | 원격 PR 상태 변경 금지 |
| Reviewer·Assignee·Label 변경 | 제외 | 원격 리소스 변경 금지 |
| CI 실행·재실행·Checks 작성 | 제외 | GitHub 쓰기 및 실행 부작용 발생 |
| Push·Force push | 제외 | 원격 브랜치 변경 금지 |

### 1.3 “GitHub 기록 없음”과 PR 조회의 관계

| 해석 | PR 목록 제공 가능 여부 | 제한 |
|---|---|---|
| GitHub 리소스 생성·변경 0건 | 가능 | 읽기 전용 API 조회 허용 |
| GitHub 요청·서버 접근 기록까지 0건 | 실시간 조회 불가 | 인증된 조회도 서버 접근 흔적 발생 가능 |
| 리뷰 데이터만 GitHub에 저장 금지 | 가능 | 원격 쓰기 금지 범위를 별도 확정 필요 |

**권고 기본값:** “플러그인과 플러그인이 실행한 AI 작업에 의한 GitHub 리소스 변경 0건”으로 정의. PR 조회 과정의 요청·접근 로그는 이 보장에 포함하지 않는 것으로 명시.

- GitHub 조회 기능 비활성화 시 GitHub 요청 0건 필요.
- GitHub 조회 활성화 시 인증된 읽기 전용 요청만 허용.
- 기존 GitHub PR 상세에서도 새 코멘트는 로컬 세션에만 저장.
- 원격 PR 본문·댓글과 로컬 리뷰 코멘트에 서로 다른 출처 표시 필요.

“전체 프로젝트”는 기본적으로 **Orca에 등록된 모든 저장소**로 해석. GitHub 계정·조직의 전체 저장소 탐색은 후속 범위.

## 2. 페르소나·사용 시나리오

### 2.1 페르소나

| 항목 | 정의 |
|---|---|
| 사용자 | Orca에서 Claude 또는 Codex로 개발하는 1인 개발자 |
| 작업 환경 | 여러 저장소·worktree·브랜치를 동시에 관리 |
| 주요 목적 | PR 생성 전 변경 내용을 직접 읽고 수정 지시를 남기는 작업 |
| 주요 불편 | diff 확인과 에이전트 수정 지시 간 파일·라인 정보 재작성 |
| 성공 기준 | 로컬 코멘트 작성 → AI 수정 → 재검토 완료, GitHub 리소스 변경 0건 |

### 2.2 PR 생성 전 기본 흐름

| 단계 | 사용자 동작 | 시스템 동작 |
|---|---|---|
| 1 | Orca에서 대상 worktree 선택 | 선택 worktree의 ID·경로·저장소 확인 |
| 2 | 커맨드 팔레트에서 Local Self Review 열기 | 로컬 서버 시작 또는 재사용, 내장 브라우저 탭 열기 |
| 3 | 비교 기준 선택 | 기본 base 후보 표시, 브랜치·작업 디렉터리 상태 수집 |
| 4 | 리뷰 세션 생성 | 커밋 SHA·파일 상태·diff 스냅샷 저장 |
| 5 | 파일별 변경 확인 | 파일 목록·diff·추가/삭제 통계 표시 |
| 6 | 라인을 드래그하고 코멘트 작성 | 파일·side·시작/끝 라인·문맥을 함께 저장 |
| 7 | Claude 또는 Codex 선택 후 리뷰 완료 | 실행 대상 코멘트 수·경로·제외 항목 표시 |
| 8 | AI 수정 실행 | 저장된 코멘트로 프롬프트 생성, 실행 ID 발급 |
| 9 | 결과 확인 | 종료 상태·변경 파일·실행 로그·새 diff 표시 |
| 10 | 코멘트별 수정 여부 재검토 | 사용자 확인으로 스레드 resolved 처리 |
| 11 | 세션 완료 | 로컬 완료 상태 저장; PR 생성은 별도 작업 |

### 2.3 기존 PR 조회 흐름

- 등록 저장소 전체의 open PR 목록 조회, draft 여부 배지 표시.
- 저장소·작성자·draft 여부 필터 제공.
- PR 선택 시 제목·본문·base/head·파일 변경 상세 조회.
- 대응하는 로컬 worktree가 있을 때 로컬 리뷰 세션 연결 가능.
- 로컬 worktree가 없으면 원격 읽기 전용 상세 제공; 자동 checkout·clone 없음.

## 3. 기능 요구사항

P0: 1차 릴리스 필수. P1: 2차 릴리스. P2: 이후 확장.

| ID | 기능 | 우선순위 | Acceptance Criteria |
|---|---|---|---|
| FR-01 | 리뷰 UI 열기 | P0 | 인자 없는 Orca 커맨드 실행으로 내장 브라우저에 리뷰 UI 표시; 워커 커맨드 10초 이내 반환 |
| FR-02 | 저장소·worktree 식별 | P0 | CLI 결과의 worktree ID·repo ID·경로 표시; 대상 변경 시 기존 세션 경로 자동 변경 없음 |
| FR-03 | 비교 기준 선택 | P0 | `base...HEAD`의 merge-base 기반 변경 확인 가능; base 후보를 확인·변경 가능; 후보 없는 경우 명시 선택 전 시작 차단 |
| FR-04 | 미커밋 변경 포함 | P0 | 기본값으로 staged·unstaged·untracked 포함; 같은 파일의 staged·unstaged 변경은 현재 작업 파일 결과 기준으로 통합; untracked 제외 선택 가능 |
| FR-05 | 변경 파일 목록·diff | P0 | 추가·수정·삭제·이름 변경 파일 표시; 텍스트 diff의 old/new 라인 번호 표시; 바이너리에는 텍스트 라인 코멘트 비활성화 |
| FR-06 | 멀티라인 선택 | P0 | 같은 파일·같은 side의 연속 1~200줄 선택 가능; 파일 또는 side를 넘는 범위 생성 차단 |
| FR-07 | 코멘트 CRUD | P0 | 생성·수정·삭제 후 재시작 시 결과 복원; 코멘트 최대 10,000자; 저장 실패 시 저장 완료 표시 금지 |
| FR-08 | 스레드 상태 | P0 | open/resolved 전환 및 재열기 가능; AI 실행 성공만으로 자동 resolved 처리 없음 |
| FR-09 | 스냅샷·위치 검증 | P0 | 외부 변경 감지 시 새 스냅샷 생성 안내; 위치 확인 실패 코멘트 outdated 표시; 검토 없이 AI 지시에 포함 금지 |
| FR-10 | 리뷰 완료 및 AI 수정 | P0 | 미해결·유효 코멘트 수와 실행 worktree 표시; 중복 클릭으로 AI 작업 2건 생성되지 않음 |
| FR-11 | 에이전트 선택 | P0 | Claude/Codex 선택값 세션별 저장; 미설치·실행 불가 에이전트 선택 시 실행 차단 및 원인 표시 |
| FR-12 | 실행 상태·결과 | P0 | queued/running/succeeded/failed/cancelled/interrupted 표시; 종료 코드·변경 파일·로그 확인 가능 |
| FR-13 | 실행 취소·복구 | P0 | 취소 시 해당 실행의 자식 프로세스 종료 요청; 남은 파일 변경 표시; 재시작 시 실행 중 작업의 생존 여부 확인 |
| FR-14 | 재검토·세션 완료 | P0 | AI 실행 후 이전/현재 diff 비교 가능; open 스레드가 남으면 완료 전 확인 필요; 완료 세션 재열기 가능 |
| FR-15 | 등록 저장소 PR 통합 목록 | P0 | 설정된 조회 한도 내 모든 페이지 수집; open 상태 PR의 draft 여부 구분; 한도 초과 시 부분 조회 표시 |
| FR-16 | PR 기본 상세 | P0 | 제목·본문·작성자·base/head·draft 여부·변경 파일·diff 표시; 변경 동작 버튼 없음 |
| FR-17 | 로컬 세션 목록 | P0 | 저장소·worktree·세션 상태별 목록과 재열기 제공; worktree 삭제 후에도 저장된 세션 조회 가능 |
| FR-18 | GitHub 조회 상태 | P0 | 조회 비활성화·인증 오류·rate limit·네트워크 오류 표시; 실패 시 기존 캐시 유지 및 마지막 조회 시간 표시 |
| FR-19 | 파일별 확인 완료 | P1 | 파일별 확인 상태 저장; 파일 내용 변경 시 해당 상태 초기화 |
| FR-20 | 전체 리뷰 메모·응답 | P1 | 세션 메모와 스레드 응답 저장; 프롬프트 포함 여부 선택 가능 |
| FR-21 | PR 댓글·리뷰·Checks 조회 | P1 | 기존 원격 데이터 조회 가능; 로컬 코멘트와 출처 구분; 제출·재실행 기능 없음 |
| FR-22 | 자동 앵커 재배치 | P1 | 문맥·내용 일치 검증 후 후보 위치 제시; 모호한 후보 2개 이상이면 자동 확정 금지 |
| FR-23 | 세션 내보내기 | P1 | JSON·Markdown으로 로컬 내보내기; 인증 정보 포함 0건 |
| FR-24 | split diff·고급 필터 | P2 | unified/split 전환, 파일 경로·확장자·PR 작성자 필터 제공 |

## 4. 비기능 요구사항

### 4.1 성능·안정성

시험 기준: Apple Silicon, RAM 16GB, 로컬 SSD, 서버 준비 완료 상태. GitHub 응답 시간은 로컬 UI 성능 측정에서 제외.

| ID | 요구사항 | 검증 기준 |
|---|---|---|
| NFR-01 | 일반 diff 응답 | 100파일·변경 10,000줄에서 파일 목록 2초 이내, 첫 파일 diff 3초 이내 표시 |
| NFR-02 | 대형 diff 처리 | 2,000파일·변경 100,000줄에서 목록 5초 이내; 선택 파일만 지연 로드; 전체 diff DOM 동시 생성 금지 |
| NFR-03 | 렌더링 제한 | 화면 주변 포함 최대 500줄 단위 렌더; 단일 파일 5MB 또는 20,000줄 초과 시 제한 안내 및 선택 로드 |
| NFR-04 | 입력·저장 | 코멘트 입력 중 UI 응답 100ms 이내; 저장 500ms 이내 목표; 저장 중·완료·실패 구분 |
| NFR-05 | 비정상 종료 복구 | 저장 완료 코멘트 손실 0건; 원자적 파일 교체와 최근 3개 백업 유지 |
| NFR-06 | 중복 실행 방지 | 동일 worktree에 플러그인 AI 실행 최대 1개; 중복 요청은 기존 실행 ID 반환 |
| NFR-07 | PR 조회 부하 | 사용자 새로고침 또는 활성 목록 화면의 5분 주기 조회; GitHub 동시 요청 최대 4개 |

### 4.2 보안·GitHub 쓰기 방지

| ID | 요구사항 | 구현·검증 방법 |
|---|---|---|
| NFR-08 | 로컬 서버 접근 | `127.0.0.1`에만 bind; LAN·공인 인터페이스 listen 금지 |
| NFR-09 | UI 인증 | 256비트 난수 토큰으로 최초 인증; 이후 HttpOnly·SameSite=Strict 쿠키 사용; URL 토큰을 방문 기록에서 제거 |
| NFR-10 | 요청 검증 | 인증·Origin·Host 검증; CSRF 보호; 인증 없는 데이터 조회·수정 요청 거부 |

| NFR-15 | GitHub 조회 제한 | 전용 조회 모듈에서 승인된 REST GET 경로만 허용; 임의 URL·임의 `gh` 명령·GraphQL 호출 금지 |

| NFR-17 | AI의 원격 변경 차단 | 플러그인이 실행한 AI에도 별도 강제 실행 정책 적용; 프롬프트의 “push 금지” 문장만으로 보장 선언 금지 |
| NFR-18 | 코드 외부 전송 고지 | 로컬 저장과 AI 서비스 전송 구분; 최초 실행 전 코드 문맥이 선택한 AI 서비스에 전달될 수 있음을 표시 |

**보장 범위 구분 필요:**

- NFR-15·16으로 플러그인의 PR 조회 경로에 대한 쓰기 금지 구현 가능.
- 일반 Node 프로세스와 일반 AI CLI는 임의 프로세스·네트워크 실행 가능하므로, 현재 플랫폼 capability만으로 AI의 GitHub 쓰기까지 차단 불가.
- AI 실행까지 포함한 강한 보장을 위해 OS 격리 또는 이에 준하는 강제 실행 환경 필요. AI 서비스 통신만 허용하고 GitHub·Git 원격 통신 및 외부 에이전트 접근 차단 필요.
- CLI의 승인 설정·도구 제한은 추가 방어 수단으로 사용하되, 실제 차단 범위 검증 필요.
- 강제 격리 확보 전에는 “AI 포함 GitHub 쓰기 0건 보장” 표시 금지. 해당 보장이 필수이면 AI 자동 수정 출시 차단 조건.

“로컬 only”는 **리뷰 데이터의 저장 위치와 리뷰 UI 서비스 위치**에 적용. Claude/Codex 사용 시 코드의 외부 전송이 발생할 수 있으므로 완전한 오프라인 실행으로 표현 불가.

## 5. 플랫폼 제약 대응 아키텍처 옵션

### 5.1 옵션 비교

| 항목 | A. 오른쪽 패널 중심 | B. 내장 브라우저 + 로컬 서버 | C. 외부 브라우저 + 로컬 서버 |

| GitHub 조회 | 패널에서 직접 불가 | 서버의 전용 조회 모듈 | 서버의 전용 조회 모듈 |
| UI와 백엔드 통신 | 직접 채널 없음 | loopback HTTP | loopback HTTP |
| 워커 종료 대응 | 동적 데이터 공급 경로 부재 | 별도 서버 수명 관리 | 별도 서버 수명 관리 |

| Orca 연결 | 제한된 3개 호스트 액션 | 서버가 Orca CLI 사용 | 서버가 Orca CLI 사용 |
| 판정 | 전체 요구사항 구현 부적합 | **권고** | 내장 브라우저 호환 문제 시 대안 |

A는 도움말·현재 branch·터미널 안내 정도의 보조 패널로 사용 가능. 코멘트 저장·diff 공급·PR 조회를 위해 터미널을 데이터 통신 통로로 사용하는 구조는 보안·오류 복구·사용성 기준상 제외.

### 5.2 권고 구조

| 구성 요소 | 책임 |
|---|---|
| 플러그인 워커 | 인자 없는 커맨드 등록, 서버 시작·재사용 확인, CLI 기반 브라우저 탭 열기 |
| detached 로컬 서버 | HTTP API·UI 제공, 세션 저장, Git diff 계산, GitHub 읽기, AI 실행 관리 |
| 내장 브라우저 | 저장소·worktree 선택, diff·코멘트·PR 목록, 실행 상태 표시 |
| 파일 저장소 | 세션·스냅샷·실행 메타데이터·캐시·서버 디스커버리 |
| Orca CLI 어댑터 | 등록 저장소·worktree 조회, 탭 생성, 선택적 터미널 연동 |
| GitHub 조회 어댑터 | 허용된 REST GET 조회만 수행 |

패널 메시지의 64KB·30건/10초 제한에 diff나 실행 로그를 싣지 않는 구조.

### 5.3 커맨드 인자 없음 대응

- 커맨드 역할을 “리뷰 애플리케이션 열기”로 한정.
- 커맨드 실행 시 `orca worktree current --json`으로 초기 대상 확보.
- 세션·base·에이전트 선택은 브라우저 UI에서 수행.
- 브라우저 탭을 연 뒤 서버 API로 작업 요청 전달.
- AI 수정과 PR 조회 완료를 워커 커맨드 반환 조건으로 사용하지 않음.
- 서버 초기화 목표 5초, 탭 열기 포함 커맨드 반환 목표 10초; 30초 타임아웃 전에 실패 반환 필요.

### 5.4 서버 수명 관리

| 항목 | 요구사항 |
|---|---|
| 프로세스 분리 | 워커의 in-flight 상태에 의존하지 않는 detached 자식 프로세스 |
| 시작 중복 방지 | 플러그인 설치 인스턴스별 시작 잠금; 동시 커맨드에서도 서버 1개 |
| 워커 idle reap | 워커 종료 후 열린 UI·실행 중 AI 작업 유지 |
| 자동 종료 | 브라우저 연결 0개·AI 작업 0개·진행 요청 0개가 15분 지속되면 종료 |
| UI 연결 판단 | 30초 heartbeat, 90초 미수신 시 연결 해제 |
| 비정상 종료 | 다음 커맨드에서 재시작; 기존 AI 작업 상태와 데이터 재검증 |
| 업데이트·제거 | 버전 불일치 시 안전한 교체; 실행 중 작업이 있으면 교체 보류; 제거 훅 존재를 가정하지 않고 유휴 종료로 잔존 프로세스 정리 |
| 중복 탭 | 동일 세션 다중 조회 허용; 저장 충돌은 revision으로 거부 |

### 5.5 포트·디스커버리

- OS가 할당한 임시 포트 사용; 고정 포트 충돌 회피.
- 디스커버리 파일에 포트·PID·시작 시각·인스턴스 ID·프로토콜 버전 저장.
- 실행 상태와 인증 자료는 권한 0600의 파일로 관리.
- 서버 재사용 전 인증된 health handshake 수행.
- PID 존재만으로 서버 재사용 또는 강제 종료 금지.
- 오래된 디스커버리 파일은 handshake 실패 후 정리.
- 포트 변경 시 열린 UI에 재연결 실패와 커맨드를 통한 재열기 안내.

### 5.6 Worktree 경로 식별

| 상황 | 경로 확보 방법 |
|---|---|
| 현재 worktree | `orca worktree current --json` |
| 전체 대상 목록 | `orca repo list --json` + `orca worktree list --json` |
| 새 worktree 이벤트 | 이벤트의 path 사용 후 CLI 결과와 확인 |
| 패널 context | branch·displayName만으로 경로 추론 금지 |
| 이름 중복 | worktree ID·repo ID·정규화 경로로 식별 |
| worktree 삭제 | 저장 세션은 유지, AI 실행 차단 |
| UI 열린 뒤 포커스 변경 | 세션 대상 고정; 현재 포커스가 바뀌어도 실행 대상 변경 없음 |

`orca tab create`는 현재 worktree 스코프이므로 조회와 탭 생성 사이 포커스 변경 가능성 존재. 지원되지 않은 스코프 인자를 가정하지 않고, UI 상단의 대상 경로와 선택 기능으로 데이터·실행 대상의 정확성 확보 필요.

## 6. AI 수정 연동 설계 요구

### 6.1 코멘트 → 프롬프트 규격

| 영역 | 필수 정보 | 규칙 |
|---|---|---|
| 실행 식별 | session ID·run ID·snapshot ID | 재시도와 결과 추적 기준 |
| 작업 대상 | repo ID·worktree ID·절대 경로 | 실행 cwd와 일치 검증 |
| 비교 기준 | base ref·base SHA·head SHA·merge-base SHA | 실행 전 스냅샷 검증 |
| 파일 | 현재 상대 경로·이전 경로·변경 유형 | 이름 변경·삭제 파일 구분 |
| 라인 앵커 | old/new side·시작/끝 라인 | 범위는 양 끝 포함 |
| 코드 문맥 | 선택 라인 전체·앞뒤 20줄·해당 diff hunk | old 라인은 현재 파일 위치로 오인 금지 |
| 코멘트 | thread ID·원문·대상 범위 | 작성 내용을 임의 요약·삭제하지 않는 구조 |
| 실행 정책 | 허용 경로·GitHub 변경 금지·commit/push 금지 | 프롬프트 외 강제 정책 별도 적용 |
| 결과 요구 | 스레드별 수행 내용·미수행 이유·변경 파일·검증 결과 | 파싱 실패 시 원문 결과 보존 |

- 실행 대상: open 상태이면서 현재 스냅샷에서 유효한 스레드.
- outdated·resolved 스레드는 기본 제외.
- 삭제된 old 라인 코멘트도 삭제 판단 수정 등 유효한 지시로 사용 가능.
- 코멘트 없는 실행 차단.
- 총 프롬프트 100KB 초과 시 파일·스레드 단위 분할 안내; 조용한 잘림 금지.
- 같은 worktree의 분할 작업은 순차 실행 및 매 실행 전 스냅샷 확인.
- 코멘트의 파일 경로·셸 명령 문자열을 직접 실행 명령으로 변환 금지.

### 6.2 실행 방식 비교

| 항목 | Orca 에이전트 터미널 전송 | Headless CLI 실행 |
|---|---|---|
| 방식 | `orca terminal send`로 기존 Claude/Codex에 프롬프트 입력 | `claude -p` 또는 `codex exec`를 서버에서 실행 |
| 장점 | 기존 대화 문맥 활용, 사용자가 과정 관찰 가능 | 실행 ID·종료 코드·로그·취소 관리 용이 |
| 대상 확인 | 터미널 소유 worktree·에이전트 상태 확인 필요 | cwd·실행 파일·인자 고정 가능 |
| 완료 판정 | 전송 성공만으로 완료 판정 불가 | 프로세스 종료와 결과 수집 가능 |
| 기존 작업 충돌 | TUI가 다른 작업 중일 가능성 | 새 프로세스로 분리 가능하나 파일 충돌은 별도 관리 |
| 원격 쓰기 통제 | 기존 터미널의 권한·인증을 상속하므로 강제 보장 어려움 | 별도 격리 환경 적용에 적합 |
| 권고 | P1 선택 기능 | **P0 기본 방식** |

Headless CLI 사용 자체가 격리를 제공하는 것은 아님. NFR-17 검증을 통과한 실행 환경에서만 강한 GitHub 쓰기 금지 보장 가능.

### 6.3 실행·결과 추적

| 단계 | 요구사항 |
|---|---|
| 사전 검증 | CLI 실행 가능 여부·worktree 존재·스냅샷 일치·동일 worktree 실행 중복 확인 |
| 충돌 방지 | 시작 시 Git 상태와 대상 파일 hash 기록; 기존 dirty 변경을 기준 상태로 보존 |
| 실행 | stdin으로 프롬프트 전달 우선; 명령행 인자·프로세스 목록에 리뷰 원문 노출 최소화 |
| 상태 갱신 | running 및 최근 로그를 UI에 2초 이내 반영 |
| 완료 판단 | 종료 코드와 결과 수집; 성공 종료를 수정 내용의 정확성으로 해석 금지 |
| 변경 수집 | 실행 직전/직후 diff로 변경 파일 표시; 외부 동시 수정 가능성을 함께 확인 |
| 취소 | 해당 실행 프로세스 그룹 종료; 변경 파일 자동 삭제·reset 금지 |
| 재시도 | 새 run ID 발급; 이전 실행 파일 변경을 확인한 뒤 새 스냅샷 기준 사용 |
| 재검토 | 스레드별 결과 표시 후 사용자가 resolved 결정 |
| 장애 복구 | 서버 재시작 후 프로세스 신원 확인; 생존 확인 불가 작업은 interrupted 처리 |

브라우저 탭을 닫아도 실행은 유지. Git·파일 hash만으로 외부 에이전트의 동시 수정을 완전히 구분할 수 없으므로, 동일 worktree 동시 수정 발견 시 충돌 경고와 재검토 필요.

### 7.2 저장 스키마·위치

기본 저장 루트: `~/Library/Application Support/OrcaLocalSelfReview/`

| 위치 | 형식 | 내용 |
|---|---|---|
| `index.json` | JSON | 세션 목록·요약·schemaVersion |
| `sessions/<sessionId>/session.json` | JSON | ReviewSession·Thread·Comment |
| `sessions/<sessionId>/snapshots/<snapshotId>/` | JSON·텍스트 | 파일 메타데이터·diff·필요한 코드 문맥 |
| `sessions/<sessionId>/runs/<runId>/` | JSON·텍스트 | AIRun·프롬프트·결과·제한된 로그 |
| `cache/github/` | JSON·diff | PR 조회 캐시 |
| `runtime/<installationId>/` | JSON | 디스커버리·인스턴스 상태·시작 잠금 |
| Orca storage | 작은 KV | 기본 에이전트·UI 설정·최근 선택 |
| Orca secrets | secret | 추가 인증 정보가 필요한 경우에만 사용 |

- Orca storage의 값 256KB·총 5MB 제한 때문에 diff·세션 본문 저장소로 사용하지 않음.
- JSON에 `schemaVersion`·`revision`·UTC ISO 8601 타임스탬프 포함.
- 단일 서버가 쓰기 담당; revision 불일치 요청은 충돌 반환.
- 세션 저장 완료 후 목록 인덱스 갱신; 인덱스 손상 시 세션 파일로 재구성 가능.
- 코멘트 삭제 시 본문도 삭제; 미공개 코드·개인 메모의 불필요한 영구 tombstone 보관 없음.
- snapshots는 필요한 diff·문맥 중심으로 저장; 전체 저장소 복사 없음.

## 10. MVP 분할 제안

### 10.1 1차 릴리스

| 묶음 | FR 목록 | 제공 결과 |

| 프로젝트 개요 | FR-15~FR-18 | 전체 등록 저장소의 draft/open PR 목록·기본 상세·로컬 세션 목록 |

1차 출시 기준:

- diff 선택·코멘트 저장·재시작 복원·AI 수정·재검토의 전체 흐름 통과.
- 워커 idle reap 이후 UI와 실행 중 AI 작업 유지 확인.
- PR 조회의 GitHub 변이 요청 0건 확인.
- AI 실행까지 쓰기 금지 보장을 제공할 경우 NFR-17 강제 격리 검증 통과.
- AI 격리를 확보하지 못하면 자동 수정 부분은 출시 보류. 이 경우 제공 가능한 제품은 “로컬 리뷰·읽기 전용 PR 조회”이며, 원문 전체 요구 충족으로 판정 불가.
- 라이트·다크, 코멘트 영속성, 대형 diff 제한, 중복 실행 방지 검증 통과.
